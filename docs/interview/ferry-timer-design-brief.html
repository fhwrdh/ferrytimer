Ferry Timer: an eval harness that lets an agent tune real routing

The design as it stands after today's iterations: what's built, why each choice was made, and where the edges are.

branch feat/route-plan-sampler head e66fe47 107 tests live app not yet redeployed

Say it in 45 seconds

"My first instinct was to put an agent inside the app. I took it out of the runtime path: a commute decision has to be fast, free and give the same answer twice. Instead I put the agent in the development loop. A sampler records real traffic and ferry data every 20 minutes; a resolver turns it into what actually happened; an eval scores the routing algorithm against that truth, next to the old algorithm on the exact same trips. A coding agent then proposes changes and the harness decides — and most of the interesting work was making sure the agent can't win by gaming the harness."

Ferry Timer answers one question on the way home to the Kitsap Peninsula: take the Bainbridge ferry, the Kingston ferry, or drive around through Tacoma. It uses live Google traffic, WSDOT schedules, sailing space and vessel positions.

System at a glance

Three things run in three places. The algorithm is one pure function shared by all of them, so what the eval scores is literally what the app runs.

  1. Sample

    Cron on the droplet records PlanInputs — everything the algorithm needs, as JSON — from Downtown, Northgate and AI2 to a fixed destination. No plan is computed there; plans are computed at eval time for whichever algorithm version is being scored.

  2. Resolve

    Once a trip would be over (3.5 h after the sample), the resolver reconstructs what really happened from later samples and WSDOT's record of actual departures. No Google calls.

  3. Score

    Frozen v0 and current v1 plan every resolved sample; errors count only where both predicted. Handcrafted guardrails run first.

  4. Tune

    The tune-route-plan skill runs measure → hypothesize → change one thing → re-measure, and keeps a change only if the holdout gates pass.

Why record inputs, not predictions

If the sampler stored v1's answer, changing v1 would invalidate every sample. Recording the raw inputs means any future algorithm replays against the same history. To keep replays from going stale, the sampler prices the drive home for three candidate sailings per route, a superset of what any algorithm would pick.

Algorithm v1 — what changed from what shipped

src/lib/routePlan.ts is pure: inputs, parameters and bias in; a plan out. v0 is kept frozen beside it as the baseline.

Close call fires when the top two routes are within 15 minutes by decision time, or when ranking by decision time would change the winner. Headline stays optimistic ("go for it"); the close call stays honest about the risk.

In the app, the hook now runs two stages: the existing fetches, then Google calls priced at each chosen sailing's landing time (primary plus fallback). If a timed call fails, the plan falls back to the current-traffic leg and says so.

Real bug found on the way

WSDOT sends vessel ETAs as /Date(1789407360000-0700)/. The app did new Date(vessel.Eta) — Invalid Date — so the README's real-time delay adjustment had never run in production. Found by reading the actual payload, not the docs.

Ground truth — how "what actually happened" is built

Nobody drove these trips. Truth is proxy truth, assembled only from things observed at the time. Google can't price the past (it rejects a past departureTime), so later sampler runs stand in as the traffic record.

LegObserved from
Drive to terminalThe sample's own current-traffic reading at now
Which boat you'd catchWSDOT vessel history: first sailing whose actual departure is after arrival + 10 min, skipping one the last pre-arrival space reading showed full
CrossingWSDOT EstArrival − ActualDepart (an estimate, not a recorded arrival)
Drive homeCurrent-traffic reading from the sampler run nearest the landing, within 10 min
Drive aroundThe sample's own reading — identical to the prediction

Anything missing makes the route unresolved, never guessed. The destination is Town & Country Market in Poulsbo: a public place, so the data is shareable and nothing private is on screen.

Scoring and gates

  • Paired rows. v0 and v1 are both run live on every resolved sample. A route's error counts only where the outcome resolved and both predicted — so they're judged on identical trips.
  • Split on run time. 20% holdout by FNV-1a hash of the sample's now. Samples from different origins in one run share nearly all ferry data; hashing the sample id would leak holdout into tuning.
  • Ferry-only MAE. Drive-around error is always zero by construction, so it's excluded from gates.
  • Winner agreement counts only fully resolved samples, and a missing winner counts as wrong.
  • Holdout is totals only. The agent sees tune-set detail and its worst misses; never holdout sample ids.

A change is kept only if

GateFails when
GuardrailsAny of 4 handcrafted scenarios fails (run with frozen parameters)
AccuracyHoldout v1 ferry MAE worse than v0 by more than 2 min

Coveragev1 predicts fewer resolved ferry trips than v0

With too little data a gate prints GATE SKIPPED: insufficient data instead of quietly passing.

Keeping the agent honest

This is the part to linger on. An agent optimizing against a pass/fail signal will find the cheapest way to pass. Each defense below exists because a reviewer found a concrete way to win without improving the algorithm.

How it was built — the AI workflow itself

The build is the second example for a Skills interview: not "AI wrote it" but where AI was trusted, where it was checked, and what the checks caught.

  1. Brainstorm → spec

    Classified as architectural; trade-offs argued one question at a time; spec committed and revised twice when probes contradicted it.

  2. Probe before planning

    Real API calls settled facts: Google rejects past times, WSDOT vessel history lags ~30 min, the Routes cap is 1,000/day.

  3. Plan → one subagent per task

    Cheap models transcribed fully specified code; a separate reviewer model gated every task on spec and quality.

  4. Ledger of rulings

    Every judgment call written down with its cost if wrong, so decisions survive context loss and stay auditable.

  5. Final review on the strongest model, then one fix wave

    Whole-branch review found what task reviews couldn't see across files.

What the checks caught

  • Every WSDOT sailing arrives without an arrival time (124/124) — the sampler had been pricing the drive home 35 minutes early.
  • A non-atomic budget write mandated by the plan itself, which could stop overnight sampling.
  • The holdout leak, the not-predicting loophole, the stale baseline, the "drive wins by default" bias.
  • A subagent signing commits with its own model name instead of the required trailer.
  • The permission system blocked an unapproved production deploy — the human stays in the loop for outward-facing actions.

Known limits — say these before you're asked

Thin data

Roughly 85 samples from one afternoon and evening, about 1 in 5 in holdout. A 1–2 minute MAE change can be noise.

Phase aliasing

A fixed 20-minute grid drifts in and out of phase with sailings, so the boarding-cutoff region — where close calls and big misses live — is sparsely sampled. Future experiment: time extra runs to land at each sailing's cutoff.

Truth borrows assumptions

The resolver uses a fixed 10-minute boarding buffer and WSDOT's estimated arrivals, so the eval can't tell you the right boarding buffer. Drive-around truth equals its prediction.

Rules, not enforcement

"Only a human moves the tag" is an instruction to the agent, not something code prevents. The protected-file check needs the tag set before the session.

App

A recalculation now makes up to 9–10 Google calls against a 40/min per-IP limit. The screen's close-call banner still uses headline times, not v1's fallback rule.

Where this goes

Say it in 30 seconds

"The reusable part isn't the ferry app — it's the loop: record what the system saw, resolve what actually happened, score every change against it, and let an agent propose changes behind gates. Google already forecasts traffic, so the novel data is on the water: WSDOT publishes a live snapshot of boats and car deck space, but no history and no forecast. Keep that history and you can forecast whether you'll actually get on the 5:30 — and because WSDOT's own later readings confirm or refute every forecast, the accuracy is measured, not claimed."

Why WSDOT and not Google

  • Google already does it. Traffic history and future-time forecasts are a product you call. Re-deriving them privately is worse data at real cost.
  • WSDOT doesn't. One live snapshot of "40 spaces" can't say whether they'll be gone before you arrive. A fill rate can.
  • The economics flip when it's public. One free poller serves every user; value scales with riders, cost doesn't.
  • History can't be recovered later. Vessel history can be pulled for past days; past car deck readings are gone. Collection is the one thing worth starting early.

The AI-tooling version of "what's next"

For a Skills interview, the forward-looking answer is also about the workflow:

  • Move from "an agent tunes when I ask" to a scheduled agent that proposes changes as pull requests, each carrying the scorecard, with the eval as a required CI check and a human merging.
  • Treat anti-gaming as a first-class design problem: every metric an agent optimizes needs a paired baseline, a coverage check and a truth it can't touch.
  • Keep the pattern that worked today: independent reviewers as gates, a written ledger of judgment calls, and humans on anything outward-facing.
Name the risks with the vision

WSDOT API terms and attribution for a public service; seasonal schedules, boats out of service and holidays that break patterns; "the app said I'd make it" liability, so show odds not promises; weeks of data before forecasts are useful; and check existing ferry apps before calling it novel.

Likely questions

Why not just put an LLM in the app?

The answer has to be the same twice, instant, and free on a phone at a terminal. The model's value is in exploring changes to the algorithm with an objective verdict — so it lives in the dev loop, where a wrong idea costs a reverted commit, not a missed boat.

How do you know the ground truth is right?

It isn't "right" — it's proxy truth, labeled as such. Each leg comes from an independent observation made at the time (later traffic readings, WSDOT's actual departures). Where the truth borrows the model's assumptions — boarding buffer, drive-around — the gates exclude or the skill documents it. Missing data is unresolved, never estimated.

What stops the agent from overfitting 85 samples?

A holdout it only sees totals for, split so twin samples can't leak; guardrails that pin behavior with frozen parameters; one hypothesis per change; and an explicit instruction that 1–2 minute gains may be noise. It's still thin, and I'd say so.

What would you change with more time?

Target the boarding cutoff with scheduled sampling runs; capture real trips as scenarios; enforce the eval base in CI rather than by instruction; surface the fallback sailing in the UI; and cache home-leg prices to cut Google calls.

Where did AI help most, and where did it hurt?

Helped: transcribing fully specified tasks fast, and independent reviewers finding cross-file problems (the holdout leak, the missing arrival times). Hurt, or would have: an agent under a pass/fail signal is incentivized to game it, and subagents cut corners like signing commits with their own model name. Both argue for gates and a human on outward-facing steps.

Why a Poulsbo grocery store as "home"?

A fixed, public destination makes samples replayable and shareable without putting a real home address in the data or on screen. The algorithm doesn't assume home anywhere; destinations are a separate future feature.
